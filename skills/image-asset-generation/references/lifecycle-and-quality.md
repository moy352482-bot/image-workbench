# 资产生命周期、人工确认与最低技术检查

本文件定义逻辑资产层的行为契约。当前服务调用、积分与归档事实见 [项目集成契约](project-integration.md)；身份及固定版本引用见 [一致性规则](consistency.md)。具体输出字段以相应 Schema 为准，以下状态条件不代表已存在新的 API 或生产注册器。

## 状态表达什么

资产状态描述某个确定逻辑版本，不替代底层 Task、Job、Execution 或 Artifact 审核状态。底层的 queued、archiving、uncertain 等事实必须保留，不因抽象为资产而丢失。

| 状态 | 进入条件与含义 | 不代表什么 |
| --- | --- | --- |
| `PLANNED` | 已整理 AssetSpec、Style、Prompt 与有限生成计划；可以尚未授权、未报价或受能力限制 | 不代表模型已执行、Artifact 已登记或版本已生产落库 |
| `GENERATING` | 相应生成已获授权，服务端积分预约有效，Worker 已确认开始执行 | 仅排队不能冒充开始；不能因此推定会成功 |
| `DRAFT` | 已有可关联的真实生成结果与已登记 output Artifact，仍待质量/身份核查与正式批准 | 候选文件、退出码 0 或模型自称成功均不充分 |
| `REVIEW` | 最低技术检查已完成，拟批准版本与引用可解析，结果交给人核查 | 不代表视觉效果已获认可 |
| `APPROVED` | 用户明确批准具体输出，生产 AssetVersion 绑定可验证，批准版本选择已持久化 | 新图生成、技术检查通过、Artifact 单独审核均不自动建立完整 Approved Asset |
| `FAILED` | 当前尝试已被确认失败，保存失败类型、阶段与可恢复证据 | 不授权新增付费生成，不应抹去旧批准版本 |
| `UNCERTAIN` | 无法确认执行是否结束、结果或归档事实是否完整 | 不能等同失败、自动退费或自动重试 |

本轮只有规划与离线样例；产出保持 `PLANNED`。不能以 fixture 的路径、ID 或期望结果推进生产状态。

## 状态跃迁

```text
PLANNED ──确认计划、报价与执行条件；Worker 开始──→ GENERATING
GENERATING ──真实输出生成并完成 Artifact 登记──→ DRAFT
DRAFT ──最低技术检查及版本绑定验证通过──→ REVIEW
REVIEW ──用户批准具体版本；批准选择持久化──→ APPROVED
GENERATING ──确认失败──→ FAILED
GENERATING ──执行或结果无法确定──→ UNCERTAIN
```

排队时可保持逻辑 `PLANNED` 并同时报告底层 queued。不要为了凑齐线性状态而制造假执行时间。技术检查未通过时明确指出阻塞项；有产物可保留供修复，但不能推进 APPROVED。

`UNCERTAIN` 只能在宿主核实旧执行、实际产物和归档结果后解除：确认有效输出则继续 DRAFT，确认失败则 FAILED，仍无法判断则保持 UNCERTAIN。恢复过程中不能新开模型调用去“验证是否还能生成”。

归档失败与生成失败分开处理。前者优先恢复原候选、原 execution 与原 Artifact 分配；后者如需重新调用模型，提出新的有限计划。恢复文件登记不是新的生成版本，也不代表允许改动候选图内容。

人工认为草稿不满意时，保留该版本的审阅意见；`REGENERATE` 是一个动作，不是必须插入的存储状态。`EDIT`、`NEW VERSION` 也描述操作与结果，不应伪装成现有状态枚举。

## 编辑、再生与版本保留

```text
character_001:v3（旧 APPROVED，保持可用）
  └─ 用户提出修改 → v4 的 PLANNED 提案
       └─ 新生成、检查、人工批准 → 才可选择 v4 为批准版本
```

`generation_strategy.purpose` 用 `regenerate`、`edit_version` 或 `derive_variant` 表达目的，`base_version` 保留明确父版本，目标 AssetSpec 的 `version` 使用新的可用版本号。`canonical_version` 是身份基线，不能机械改成目标版本。

已保存的规格、已有草稿和已批准版本都不原地覆盖。修改已形成的版本快照派生新版本；仅修复同次执行的归档元数据时保持该次结果身份，不重复生图。用户要求完全不同对象时应建立新的逻辑 Asset，而非沿用旧身份伪装连续性。

批准指针是未来逻辑注册表能力，目前未实现。它只能在用户选择与可验证绑定完成后移动；“最新生成”“最高版本号”或“最后写入”都不是批准规则。每个历史版本保留自身 Artifact 引用和审阅记录；切换批准选择不删除旧文件。

## 并发与幂等

当前 Job/Execution 已有请求幂等、执行检查点、积分预约和固定候选归档机制，见 [项目集成契约](project-integration.md)。Skill 必须沿用，不能通过新 request ID 绕过正在运行或状态不明的作业。

未来 host adapter 与版本注册表还需要保证以下语义；这些是设计要求，不是现有接口声明：

- 为一次确认的计划绑定稳定的操作身份；重复提交或重复回调返回同一结果，不再调用模型、不再次注册版本或扣费。
- 创建新版本时检查已有版本编号及父版本；并发提案不能覆盖同一个版本快照。
- 批准时核对用户看到的规格、Artifact 与版本绑定仍未改变；旧页面的批准不能覆盖后来发生的选择。
- 原子更新批准选择并记录原值/新值；发生冲突时返回需要处理的冲突，不能用最后写入者自动获胜。
- 登记中途失败时根据已持久化证据恢复，不复制图片来制造另一份“成功”记录。

不要求本轮发明具体事务类、锁 API 或存储表。离线规划也不能伪造这些保证已经在运行中生效。

## 两阶段人工确认与积分

第一阶段确认在生成之前。展示对象/目标版本、Style、参考用途、重要约束、能力缺口、模型调用数量和当前服务器估价。Style 的示例数量、预算上限和 `max_model_calls` 只是计划边界，不是调用授权。

现有 `CreditCostCalculator` 已由服务端维护政策；`WorkbenchState.estimate_credit` 提供任务估价，`submit(..., confirmed=True)` 预约/冻结积分。Skill 不硬编码价格、不接收客户端自报价格作为结算依据，也不把计划估价称为实际扣费。

当前没有报价快照与已确认计划哈希的强制绑定。未来适配器应保证用户确认的计划与将要执行的计划一致；计划、参考、模型、数量或价格出现实质变化时重新取得相应确认。现有有效授权不因重复读取状态而失效，但它不能扩大为任意新版本或 fallback。

成功、明确失败和不确定作业的积分状态由既有服务结算：成功消耗、明确失败退还、UNCERTAIN 保留冻结。Skill 不私自改余额，不因未看到结果就假定已经退款。只恢复归档不调用模型，但仍沿用当前提交与账本语义，不能自行宣布免计费或另行扣费。

第二阶段确认在输出后。用户检查具体图片及身份/产品一致性后，决定是否批准该版本。执行授权不包含自动批准；用户拒绝视觉结果也不意味着模型调用未发生或可以绕过账本退款。

## 最低 AssetQualityCheck 契约

`AssetQualityCheck` 是本轮定义的检查职责名称，不是当前新增可调用类。它只检查可验证的文件和登记事实，不做审美评分、自动选最佳图、人脸相似度评分或模型自评。

| 检查项 | 通过所需证据 | 未满足时 |
| --- | --- | --- |
| 生成状态 | 与本次计划相关的 Job/Execution 明确完成，返回输出清单；不只看进程退出码 | FAILED 或 UNCERTAIN，禁止声称成功 |
| 文件存在 | Artifact 可通过经授权的 Storage 解析为本次有效文件，不是任意外部路径 | 标记缺失；查原执行/归档，不重新生成掩盖 |
| 文件可读 | 文件是普通文件，内容能够验证和完整解码；读取受大小/像素限制 | 标记损坏、访问失败或超限，保留原错误 |
| 格式 | 实际格式属于当前支持的 PNG/JPEG/WEBP；不信任扩展名 | 技术检查失败，不伪造格式或静默替换 |
| 尺寸 | 实际 width/height 与登记一致；与请求的比例及尺寸要求逐项比较 | 硬要求不满足则不能通过；软目标偏差明确交人判断 |
| 内容完整性 | 文件大小与 SHA256 对应已登记 Artifact，参考/基底未被篡改 | 停止批准，查明不一致；不覆盖登记值消除差异 |
| Artifact 登记 | 存在真实 output Artifact；project/task/source 关系与本次请求一致，输出数量符合计划 | 候选不等于登记结果，优先恢复归档 |
| Version 登记 | 未来宿主能解析目标逻辑版本、规格快照、`artifact_ids` 与父版本关系，并确认未覆盖旧版本 | 明确未绑定/未实现；不能宣称完整资产检查通过 |

当前 TaskRunner/Storage 已覆盖许多文件、格式、哈希及 Artifact 校验，复用其结果并核对关联证据；不要另建文件管理或重复登记。当前没有生产 AssetVersion 注册器，因此版本检查在本轮只能验证规划结构，不能给出生产“已通过”。

对精确尺寸或原生 mask 等当前 Backend 不支持的硬要求，首先在执行前拦截能力不匹配；生成后的检查不能补救未经同意的降级。不要自动裁剪、放大、擦除或重新生成来让检查表看起来通过。

技术结果应区分已验证、失败、未知和未适用；每个判断有可追溯的标识或脱敏理由。不得将未知写成通过，不能因为没有图就给视觉质量零分，也不能把 fixture 检查提升为真实文件检查。

## 进入批准前的最终核对

1. 用户批准的是具体版本和实际输出，而非通用 Prompt 或抽象风格。
2. 最低技术检查有真实证据；引用了正确账号/工作空间内的 Artifact。
3. Artifact 人工审核与未来 AssetVersion 绑定均可验证；当前仅有 Artifact 审核时如实报告能力差距。
4. 旧批准版本未被改写；新的批准选择与用户的版本选择一致，冲突已处理。
5. 记录结果关联标识与必要审阅意见，不复制真实日志、图片或凭证到公开示例。

本轮停在规划、契约和离线测试，不推进真实生产生命周期。文件/Artifact 能力的源码定位见 [项目集成契约](project-integration.md)，人物与产品属性变更规则见 [一致性规则](consistency.md)。
