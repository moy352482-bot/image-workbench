# 图片 API 同内容重试与多用户任务并发

## 请求与实现

用户要求失败时以相同内容重试，并实测 API 并发；随后明确希望多用户按任务并行数共享执行能力。

重试属于既有 Provider，沿用 `BackendRequest` 和 `ImageAPIBackend`，不修改 Core。
请求在第一次调用前编码一次，后续使用完全相同的字节，包含默认 Skill、风格、比例、基底及参考图。
每个任务最多 3 次尝试，第一次失败等 2 秒、第二次失败等 5 秒；`Retry-After` 秒数更长时遵守该值。
所有等待和调用共用原总超时。明确审核拒绝、429、500/502/503/504、连接建立失败可重试；
鉴权或参数错误、读写超时、传输中断、无效产物不自动重发。

重试仍是原任务、原执行、原积分预约。成功只归档一份结果并结算一次网站积分；最终失败按原规则退款。
上游实际 API 收费由供应方决定。每次尝试的状态、耗时及等待记录在原诊断文件，Key 继续脱敏。
没有新增持久模型或公开 HTTP 字段。停机重启不自动重做已执行模型请求；归档恢复不调用模型。
失败后也可手动选择“重试生成”使用原需求，或“修改需求后新建”。

并发属于部署配置，使用既有 `SchedulingPolicy`、`RemoteQueue`、`IdentityStore` 和 `RemoteWorker`：
全站 `IMAGE_WORKBENCH_MAX_ACTIVE_TOTAL=4`、每账号 `IMAGE_WORKBENCH_MAX_ACTIVE_PER_ACCOUNT=4`，
一个账号可占用空闲的全部 4 位，多用户共享全站上限。按照任务保存/提交顺序领取，4 项之外继续排队。
不按用户创建 Worker，也不无限制提高同时请求数。原 Worker 保留，额外实例 2/3/4 使用独立缓存目录。
任务和产物的 Workspace 权限、各账号账本继续由原服务处理；处于 `uncertain` 的任务仍占位，避免重复生成。

## 真实 API 测试

2026-10-23 21:30–21:31（Asia/Shanghai）从实际云服务器发起，模型 `gpt-image-2`。
1、2、4 路依次测试，共 7 次付费 API 请求；所有请求内容相同、1:1、1024×1024，默认图片 Skill 生效。
测试关闭自动重试，7 次均首次 HTTP 200，并成功解码为图片。本轮未测试参考图编辑的并发极限。

| 同时请求数 | 成功数 | 单张耗时范围 | 全部完成耗时 | 本轮吞吐（张/分钟） |
| --- | --- | --- | --- | --- |
| 1 | 1/1 | 17.36 秒 | 17.36 秒 | 3.46 |
| 2 | 2/2 | 23.31–24.14 秒 | 24.14 秒 | 4.97 |
| 4 | 4/4 | 17.93–39.20 秒 | 39.20 秒 | 6.12 |

结论是已验证至少 4 路请求可同时成功，不能据此宣称最大并发为 4 或长期稳定吞吐。
4 路的吞吐约为单路的 1.77 倍，单个慢请求会影响整批完成时间。网站仍保留队列，只把可同时执行数调为 4。
测试前后线上业务作业计数一致，没有创建生产测试账号或任务；产物在独立测试目录保存。
下载结果时一次 SCP 超时，后续只补传缺失/不完整文件；没有再次调用模型，7 张图的哈希全部匹配。

可复用脚本：`scripts/benchmark_image_api.py`，真实测试必须显式传 `--allow-image-generation`。
不带授权参数不会访问付费接口；输出目录不能已存在，防止误把重复测试覆盖成一次结果。

```powershell
.venv/Scripts/python.exe -X utf8 scripts/benchmark_image_api.py --config deploy/image-api.local.json --output work/image-api-benchmark-new --levels 1 2 4 --allow-image-generation
```

原始证据：`work/image-api-concurrency/image-api-concurrency-86577456c93b4f958eee2e3dfcc13733/results/report.json`，
同目录保存请求内容与 7 张图。API Key 不写入报告。
